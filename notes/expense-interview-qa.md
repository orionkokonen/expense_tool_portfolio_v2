# 面接で聞かれる質問想定

Q1: 何を作ったか
Streamlitで作った、経費精算チェックツールです。
やることは大きく3つあります。
1つ目が「取り込み」。 CSVファイルで経費データを読み込みます。
2つ目が「チェック」。 これは2段階になっていて、
まず日付や金額の入力ミスを検出する基本チェック
次に禁止ワード・上限額超過・未登録カテゴリなどを検出する社内ルールチェック
を順番に行います。ルールは rules.json という外部ファイルで定義しているので、コードを変えずにルールだけ差し替えられます。
3つ目が「出力」。 チェック結果と月別・カテゴリ別の集計を、CSV・Excel・HTMLの3形式で出力します。
画面はStreamlitで作っていて、アップロードからダウンロードまで一画面で完結します。CLIからも同じ処理を実行できるので、バッチ処理にも対応しています。


Q2: なぜ作ったか
シンプルに見えて、実務に必要な要素がひと通り入っているからです。
具体的には、
CSVの取り込みと入力チェックによるデータバリデーション、
rules.jsonによるビジネスルールの外部定義、
月別・カテゴリ別などの集計ロジック、
CSV・Excel・HTMLの複数形式での出力、
数式インジェクションやXSSなどのセキュリティ対策、
そしてpytest・ruff・mypy・GitHub ActionsによるCI/CDです。
「入力 → チェック → 加工 → 出力」という業務システムの基本的な流れを一本のパイプラインで実装し、
それぞれの工程をきちんと説明できることを重視しました。

Q5: 工夫した点
工夫した点は大きく3つあります。

1つ目は、「エラー」と「警告」を明確に分けた設計です。
日付や金額の形式ミスは「エラー」として処理を止め、未登録カテゴリや上限超過は「警告」として人の判断に委ねる、という2段階にしています。
こうすることで、「止めるべき問題」と「確認すればOKな問題」を混同せずに扱えます。

2つ目は、セキュリティ対策を出力の各形式ごとに入れた点です。
具体的には3つあって、
・CSV出力時の数式インジェクション対策（セル先頭の =, +, @ にシングルクォートを付加）
・HTMLレポートのXSS対策（html.escape + Script内のJSON埋め込みで </script> の無害化）
・ユーザー入力パスのパストラバーサル対策（Path.resolve + is_relative_to でプロジェクト外への参照を拒否）
経費データはCSVで受け取って、CSV・Excel・HTMLで出力するので、出口ごとに異なる攻撃手法がありえます。
それぞれの出力形式に合わせた対策を入れました。

3つ目は、ルールをコードから切り離した点です。
禁止ワード・上限額・許可カテゴリなどをrules.jsonで外部定義し、コードを変えずにルールだけ差し替えられるようにしました。
さらに、rules.jsonの読み込み時にはバリデーションを入れて、型や値が不正な場合は明示的にエラーを出すようにしています。
「設定ファイルの中身を信用しない」という原則を意識しました。


Q6: 苦労した点

一番苦労したのは、出力形式ごとにセキュリティ対策が違うことです。

このツールはCSV・Excel・HTMLの3形式で結果を出力しますが、
それぞれ守るべきポイントがまったく違いました。

・CSV / Excel → 数式インジェクション対策
セルの先頭が = + - @ だと数式として実行されてしまうため、
書き出し直前に sanitize_cell() で先頭にシングルクォートを付けて無害化しました。
ただし "-500" のような負の数値は正当な金額なので壊さないよう、整数判定で除外しています。

・HTML → XSS（クロスサイトスクリプティング）対策
CSVの中身をそのままHTMLに埋めると <script>alert(1)</script> が実行されてしまうため、
テーブル表示では escape() で < を &lt; に変換しています。
さらに、Chart.js にデータを渡す部分では "</script>" でスクリプトタグが閉じてしまう問題があり、
\_safe_json_dumps() で "</" を "<\/" に置換する対策も入れました。

・パス入力 → パストラバーサル対策
ユーザーが "../../etc/passwd" のようなパスを入力できてしまうため、
safe_resolve() で resolve() → is_relative_to() の順にチェックし、
プロジェクト外を指していたらブロックするようにしました。

1つ1つの対策は理解できても、「どの出力にどの対策が必要か」を整理し、
抜け漏れなく組み合わせるのが一番難しかったです。
対策の方針としては「外部に出す直前で安全処理をかける」に統一し、
内部処理では生データのまま扱うことで、対策の漏れや二重適用を防ぎました。

Q7: 今後の改善点
今後の改善点は大きく3つ考えています。

1つ目は、レシートOCR取り込みです。
現在はCSVファイルでの取り込みのみですが、レシート画像から日付・金額・支払先を自動抽出して申請フォームに反映する機能を考えています。
手入力の手間とミスを同時に減らせるので、ツールとしての実用性が大きく上がると考えています。

2つ目は、承認ワークフローです。
実際の経費精算では「申請 → 上長承認 → 経理確認」という流れがあります。
今のツールはチェックと集計までですが、申請から承認までのステータス管理を加えることで、業務フロー全体をカバーできるようになります。

3つ目は、ダッシュボード表示です。
今月の申請件数、未承認件数、カテゴリ別の合計金額などをトップ画面で一覧できるようにしたいと考えています。
現在もHTMLレポートで集計は出せますが、リアルタイムに状況を把握できるダッシュボードがあると、管理者視点での利便性が上がります。
