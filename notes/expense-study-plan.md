想定面接Q&A（5問だけ）
Q1.「なぜ7段階に分けているんですか？」
A. 各ステップが1つの仕事しかしないようにするためです。

専門用語補足:これを「単一責任の原則(Single Responsibility Principle)」と言います。1関数=1役割。

Q2.「②check_rows と ⑤apply_rules、どちらも"チェック"ですよね？何が違うんですか？」
ここが最重要ポイントです。面接で必ず聞かれます。

項目 ②check_rows ⑤apply_rules
何をチェック? 形式(日付の書式、金額が整数か) 社内ルール(未登録カテゴリ、上限超過)
失敗したら errors に分けて、後工程から除外 warnings に分けるが、データは残す

A. 「形式エラーは"そもそも処理不能"なので除外。ルール違反は"処理はできるけど人が確認すべきもの"なので残す」という設計です。

Q3.「なぜ形式エラーを"早い段階で"除外するんですか？」
A. 後ろの処理(④以降)を安心して書けるからです。
たとえば「金額が整数」が保証されていれば、集計のときに int(金額) で例外が出る心配をしなくていい。
もし途中で混じっていたら、各処理に try/except を散らかすことになり、コードが読みにくくなります。

専門用語補足:これを「早期リターン」「前提条件を絞り込む」と言います。

Q4.「③normalize_ok_rows って何のためにあるんですか？」

これを数値や日付の型に変換するのが normalize_ok_rows です。
②でOKと確定した行だけに変換するので、変換途中で失敗する心配がない、というのがミソです。

### 3. CLI と GUI の2入口構成を理解する（「同じパイプラインを共有している」が言えればOK）

まず30秒で言えるべき結論

このアプリには入口が2つあります。ターミナルから動かす CLI(expense_tool.py) と、ブラウザ画面から動かす GUI(app.py) です。見た目はまったく違いますが、内側で動いているデータ処理の流れ（読み込み → 検証 → ルール判定 → 集計 → 出力）はまったく同じものを呼んでいます。これを「同じパイプラインを共有している」と言います。

用語の整理（初心者向け補足）

CLI（Command Line Interface） = コマンド入力でアプリを動かす方式。黒い画面に python expense_tool.py report data.csv のように打ちます
GUI（Graphical User Interface） = ボタンや入力欄など、画面を見ながらマウス操作で動かす方式。Streamlitはブラウザに画面を出します
エントリポイント = アプリの「入口」になるファイル。プログラムの実行はここから始まります
パイプライン = 「順番に流れていく処理の連なり」。工場の流れ作業のイメージで、CSVが「読み込み → 検証 → 集計 → 出力」と一方向に流れていきます
入口①：CLI expense_tool.py

ターミナルから次のように動かします。

python expense_tool.py report data/expenses.csv --top-n 10
expense_tool.py:90-99 の main() がCLIの入口で、引数（report、CSVパス、--top-nなど）を受け取って解析しています。引数の定義は expense_tool.py:48-76 の build_parser() にまとまっています。

特徴は、

バッチ処理やCI（自動テスト基盤）から呼びやすい
終了コード（0=正常、2=エラーあり）を返すので、自動化と相性がいい expense_tool.py:166-167
画面表示がないぶん軽量で、定期実行向け
入口②：GUI app.py

ブラウザに画面を出すStreamlitアプリです。次のように起動します。

streamlit run app.py
app.py:903 の main() がGUIの入口です。サイドバーのファイルアップローダーやボタンで操作します（app.py:912-941）。

特徴は、

CSVをドラッグ＆ドロップでアップロードできる
結果が4つのタブ（概要・検証・集計・ダウンロード）で見やすく表示される
プログラミングを知らない人でも触れる
「同じパイプラインを共有している」の中身

CLIもGUIも、CSVをもらってから出力するまでの「中身の処理」はまったく同じ関数を呼んでいます。具体的には次の5ステップ。

CSVを読み込む（read_csv）
入力チェックする（check_rows … 必須列・日付・金額の形式エラーを検出）
ルールJSONを読む（load_rules）
重複検出＋社内ルール判定（find_duplicate_candidates + apply_rules）
集計してCSV/Excel/HTMLに書き出す（make_summary、write_csv、write_xlsx_report、write_html_report）
CLI側はこの5ステップを expense_tool.py:120-197 で直接呼び出しています。

GUI側はこの5ステップをまとめて app_helper.py:131-236 の run_pipeline() という関数に切り出してあり、app.py:976 でその関数を呼んでいます。

つまり、

CLI → expense_tool.py の main() → 中の処理を順に呼ぶ
GUI → app.py の main() → app_helper.py の run_pipeline() → 中の処理を順に呼ぶ
呼び出し経路は違いますが、最終的に動かしている関数（read_csv、check_rows、apply_rules、make_summary など）はぜんぶ同じファイル（expense_core.py、rules.py）にある同じ関数です。

なぜ「2つの入口」を用意したのか

それぞれ得意な使い方が違うからです。

CLI = 自動化、定期実行、CI、エンジニアが使う想定
GUI = 一回ぽっきりの確認、現場の人が使う想定（プログラミング知識が要らない）
「使う人」と「使うシーン」が違うので、見た目（入口）は分けつつ、中身（処理）は一本化する、という設計です。

なぜ「パイプライン共有」が設計として偉いのか（面接の本丸）

ここが一番アピールポイントです。

仮にCLIとGUIで処理を別々に書いてしまうと、

ルールを1つ追加するのに2箇所を直さないといけない
片方を直し忘れて、CLIとGUIで結果が食い違うバグが起きる
テストも2倍書かないといけない
これを避けるために、「画面の作り方」と「データ処理」をはっきり分けてあります。これを 関心の分離（Separation of Concerns） や DRY原則（Don't Repeat Yourself = 同じことを2回書くな） と呼びます。

具体的には、

expense_core.py と rules.py = データ処理の本体（共通部品）
expense_tool.py = CLI用の入口（引数の受け取りだけ）
app.py = GUI用の入口（画面の組み立てだけ）
app_helper.py = GUIから共通部品を呼ぶための薄い橋渡し
入口は薄く、中身は1つ、という構造になっています。

面接想定Q&A

Q：なぜCLIとGUIの2つを用意したんですか？

A：使う人と用途が違うからです。CLIは自動化やCIから呼びやすく、GUIはプログラミングを知らない人でも触れます。ただし中の処理は同じなので、一方だけ機能が古いといった食い違いは起きないように設計しています。

Q：「同じパイプラインを共有」ってどういう意味ですか？

A：CSVを読んで、検証して、ルール判定して、集計するまでの一連の処理を、CLIとGUIで同じ関数を呼んで実現しています。CLIは expense_tool.py の main() から、GUIは app_helper.py の run_pipeline() 経由で、最終的に expense_core.py と rules.py にある同じ関数群を呼び出します。

Q：なぜ app_helper.py という別ファイルに切り出したんですか？

A：app.py は画面の描画とイベント処理に専念させ、データ処理は別ファイルに分けるためです。こうすると、画面の見た目を変えても処理ロジックには触らずに済むし、その逆も成り立ちます。これを「関心の分離」と呼びます。

Q：CLIとGUIで結果が違う、ということは起きないんですか？

A：起きにくい設計にしています。最終的に呼ぶ処理関数が同じなので、ロジックを直すときは1箇所を直せば両方に反映されます。ただし入口の引数解釈や出力ファイル名のルールは別なので、そこは個別にテストしています。

## 【ユニット4】

### 1. Excel の数式インジェクション対策 → sanitize_cell

【ユニット4-1】Excel の数式インジェクション対策 → sanitize_cell

ステップ1: そもそも「数式インジェクション」って何？

専門用語の補足から行きます。

インジェクション: 英語で「注入」。攻撃者が悪意のあるコードを注入して、システムに意図しない動作をさせる攻撃の総称。
数式インジェクション (別名: CSV Injection / Formula Injection): ExcelやGoogle Sheetsが「セルの先頭が = だと数式として計算する」性質を悪用する攻撃。
具体例:
CSVファイルにこんな1行が入っているとします。

=cmd|'/c calc.exe'!A1
これをExcelで開くと、Excelは「= で始まってる！数式だ！」と解釈してしまい、最悪の場合、外部コマンド（電卓を起動するくらいなら可愛いですが、ウイルスのダウンロードとかも理論上可能）が実行されてしまう。

つまり、「ユーザーがアップロードしたCSVを、こちらでExcelに変換して別の人に渡す」というこのアプリの作りだと、攻撃者がCSVに罠を仕込めるリスクがあるわけです。

ステップ2: 何を「危険な先頭文字」とみなすか

expense_core.py:276-295 の sanitize_cell を見てください。

危険視している先頭文字は4つ:

= … 数式の開始記号（一番典型的）

- … 数式の開始記号として解釈されることがある
  @ … 関数呼び出しの開始記号として解釈されることがある（古いExcel仕様）

* … 数式（引き算）として解釈される可能性がある
  ただし - だけは特別扱い。なぜなら -500 のような負の金額は正当なデータ なので、壊してはいけない。

expense_core.py:289-294:

if value[0] == "-":
try:
int(value) # 数値に変換できる？
except ValueError:
return f"'{value}" # できない＝怪しい文字列なのでクォート付与
「- で始まるけど int() で数値化できる → 普通の負数なのでそのまま」「数値化できない → 怪しいのでクォート付与」という判断をしています。

ステップ3: どう無害化するか（対策の本体）

対策はめちゃくちゃシンプル。先頭に ' (シングルクォート) を1個付けるだけ。

return f"'{value}"
Excelには「セル値の先頭の ' は『これはテキストだよ』という宣言として扱う」という仕様があり、' は表示されず、中身は数式評価されません。

例:

入力: =SUM(A1:A10) → 出力: '=SUM(A1:A10)
Excelで開くと: =SUM(A1:A10) というただの文字列として表示される（計算されない）
ステップ4: どこで使われているか（呼び出し側）

excel_export.py:101-106:

for r in rows:
ws.append([
sanitize_cell(str(v)) if isinstance(v := r.get(c, ""), str) else v
for c in columns
])
ここで重要なポイント:

文字列のセルだけ sanitize_cell を通している (isinstance(..., str) で判定)
数値や日付など、もともと文字列じゃないものはそのまま書き込む

### 2. HTML の XSS対策 → escape()

そもそもXSSって何？

XSS = クロスサイトスクリプティング、と読みます。
ざっくり言うと「Webページに悪意のあるJavaScriptを紛れ込ませて、見た人のブラウザで勝手に実行させる攻撃」のことです。

例えばこんな経費データがCSVに入っていたとします。

日付,カテゴリ,金額,メモ
2025-01-01,交通費,500,<script>alert("乗っ取り成功")</script>
このメモ欄をそのままHTMLに貼り付けると、ブラウザは <script> タグを「JavaScriptとして実行しろ」という命令だと解釈します。
結果、レポートを開いた人のブラウザでアラートが出る…ぐらいなら可愛いですが、実際には「Cookieを盗む」「別のサイトに勝手に飛ばす」みたいな悪さができてしまいます。

ポイントは、攻撃者は本人のPCではなく、レポートを見る人(=被害者)のブラウザでスクリプトを実行できること。だから「クロスサイト(サイトをまたぐ)」と呼ばれます。

このプロジェクトのどこで対策している？

html_report.py:215 の1行が主役です。

tds = "".join(f"<td>{escape(str(r.get(c, '')))}</td>" for c in columns)
注目するのは escape(...) の部分。これはPython標準ライブラリ html モジュールの関数で、ファイル冒頭でこう読み込まれています。

from html import escape # html_report.py:13
escape() は何をしているのか

html.escape() は、HTMLで特別な意味を持つ文字を、ただの文字に化かす関数です。具体的にはこの変換をします。

元の文字 変換後 なぜ危ないか
< &lt; タグの開始記号

>     &gt;	タグの終了記号
>
> & &amp; エスケープ自体の開始記号
> " &quot; 属性値を囲むダブルクォート
> ' &#x27; 属性値を囲むシングルクォート
> &lt; のように書くと、ブラウザは「これはタグじゃなくて、画面に表示する文字としての < だな」と解釈してくれます。

つまり先ほどの <script>alert("乗っ取り成功")</script> は、escape を通ると

&lt;script&gt;alert(&quot;乗っ取り成功&quot;)&lt;/script&gt;
になり、ブラウザはそのまま文字として表示するだけで、実行はしません。

コードを1行ずつ追う(html_report.py:212-216)

ths = "".join(f"<th>{escape(c)}</th>" for c in columns) # ヘッダ
trs = []
for r in rows:
tds = "".join(f"<td>{escape(str(r.get(c, '')))}</td>" for c in columns) # データ
trs.append(f"<tr>{tds}</tr>")
columns は列名のリスト(例: ["日付", "カテゴリ", "金額", "メモ"])
r.get(c, '') はその行の該当カラムの値を取り出す。値が無ければ空文字 ''
str(...) で必ず文字列に変換(escapeは文字列しか受け取れないため)
escape(...) で危険文字を無害化
f文字列で <td>...</td> の形に組み立て
ヘッダ(<th>)とデータ(<td>)の両方でescapeを通しているのがミソです。「ヘッダは固定値だから安全」と思っても、列名がユーザー入力CSV由来だったら危ないので、両方守っています。

面接で聞かれたらこう答える(模範解答)

Q: HTMLレポートでXSS対策はどうしてる？

A: html_report.py でテーブルを生成するとき、セルの値を全部 html.escape() に通しています。CSVの中身に <script> タグが入っていてもブラウザが実行せず、ただの文字として表示されるようになります。ヘッダ列も含めて全セルに適用しているのがポイントです。

Q: なぜそれが必要？

A: CSVは外部から来るデータなので、悪意のある文字列が混じる可能性があります。HTMLにそのまま貼ると、ブラウザがタグとして解釈してJavaScriptを実行してしまう恐れがある、いわゆるXSS攻撃のリスクがあります。

Q: escape() だけで完璧？

→ この最後の答えが他の応募者と差がつくポイントです。「escapeで全部OK」と答える人が多い中で、「埋め込み先がHTMLの本文かscriptタグかで対策が違う」と言えると、セキュリティをちゃんと理解している印象になります。

### 3. </script> 突破型XSS対策 → \_safe_json_dumps

ステップ1: そもそも何をしているコードか（背景理解）
該当コード html_report.py:26-39

def \_safe_json_dumps(data: list[str] | list[int]) -> str:
return json.dumps(data, ensure_ascii=True).replace("</", r"<\/")
このツールは集計結果をHTMLレポートに出力します。そのときグラフを描くために、Pythonで集計したデータ（月のラベルや金額のリスト）を、HTML内の <script> タグの中にJavaScriptの変数として埋め込む設計になっています。

実際に埋め込んでいる箇所 html_report.py:158-161

const monthLabels = {\_safe_json_dumps(month_labels)};
const monthValues = {\_safe_json_dumps(month_values)};
ここの {...} はPythonのf-stringで、実行時に文字列が差し込まれます。
たとえば month_labels = ["2026-01", "2026-02"] なら、

const monthLabels = ["2026-01", "2026-02"];
というJavaScriptコードがHTMLに書き込まれます。これをブラウザが読んでChart.jsでグラフを描く、という仕組みです。

専門用語の補足:

f-string … Python独自の文字列の書き方。f"今は{x}時" で変数を埋められる
JSON … JavaScriptが理解できるデータ形式。["a","b"] のような書き方
CDN … ライブラリをネット経由で配信する仕組み（自分でファイルを置かなくていい）
ステップ2: ふつうの json.dumps() だと何が危ないか
ここが核心です。

CSVの中身は外部から来るデータなので、悪意ある文字列が入っているかもしれません。たとえばカテゴリ名にこんな文字列が入っていたとします:

</script><script>alert('攻撃')</script>
これを ふつうの json.dumps() だけで HTMLに埋め込むと、出力されるHTMLはこうなります:

<script>
  const catLabels = ["</script><script>alert('攻撃')</script>"];
</script>
ブラウザはHTMLを上から読むとき、文字列の中だろうが何だろうが、最初に見つけた </script> で「ここでscriptタグが終わった」と判断します。

つまりブラウザにはこう見えてしまう:

<script>
  const catLabels = ["    ← ここでscriptが終わったと誤認
</script>
<script>alert('攻撃')</script>   ← これが実行される！

"];</script> ← 残りはゴミとして無視
結果、alert('攻撃') が実行されてしまう。これが XSS（クロスサイトスクリプティング）攻撃 です。

ステップ3: なぜ escape() では解決できないのか（面接のキモ）
ユニット4の2番で出てきた html.escape() は、< を &lt; に変換する関数です。テーブルのセルに使うのは正解。

ところが <script> タグの中身で escape() を使うと、JavaScriptとして文法が壊れます。

const catLabels = ["&lt;script&gt;"]; // 表示が&lt;になっておかしい
JavaScriptは &lt; をHTMLエスケープと解釈してくれません。文字列として &lt; という7文字が入ったまま扱います。データが壊れる。

つまり、

HTMLのテーブル本文 → escape() でOK

<script> タグの中 → escape() ではダメ。別の対策が必要
これが _safe_json_dumps が独立して存在する理由です。

ステップ4: _safe_json_dumps の2つの工夫

return json.dumps(data, ensure_ascii=True).replace("</", r"<\/")
工夫1: ensure_ascii=True
日本語などの非ASCII文字を \u30A2（カタカナの「ア」）のような Unicodeエスケープ表記に変換します。

例: "アメリカ" → "\u30a2\u30e1\u30ea\u30ab"

これによりJSON文字列の中に < や > などのHTML特殊文字が混ざりにくくなり、安全性が一段上がります。日本語のサイトでは特に効きます。

工夫2: .replace("</", r"<\/") ← これが本命
文字列中の </ をすべて <\/ に置き換えます。

r"<\/" の r は raw文字列（バックスラッシュをそのまま扱う書き方）
JavaScriptでは "<\/script>" と "</script>" は 文字列としては全く同じ意味（\/ は / のエスケープで、結果は /）

でも HTMLパーサー（ブラウザ）から見ると <\/script> は </script> と認識されない
つまり、

見る人 <\/script> の解釈
ブラウザのHTMLパーサー scriptの終了タグではない（無視して文字列として扱う）
JavaScriptエンジン </script> という文字列として読む（意味は同じ）
この 「両者で解釈が違う」 という性質を利用して、ブラウザに「ここでscriptが終わった」と誤認させない工夫になっています。

ステップ5: 面接で聞かれたらこう答える（30秒テンプレ）
「HTMLレポートでは集計データを <script> タグ内にJSONで埋め込んでグラフを描いています。ここで普通の json.dumps をそのまま使うと、データに </script> が含まれていた場合、ブラウザがそこでscriptタグが終わったと誤認して、後続の文字列がHTMLとして実行されてしまうXSSの危険があります。テーブル本文に使う html.escape() は <script> タグ内では文法を壊すので使えません。そこで \_safe_json_dumps を作り、ensure_ascii=True で日本語を \uXXXX 化し、</ を <\/ に置換することで、ブラウザに終了タグと誤認させない設計にしています。」

差別化ポイントとして言えると強いのは:

「escape() だけでは足りず、<script> の中は別対策が要る」 という設計判断
「<\/ はJSとしての意味は変わらないが、HTMLパーサーは終了タグと認識しない」 という仕組みの理解
ステップ6: 復習チェックリスト
HTML内の <script> タグにJSONを埋め込む設計だと答えられる
攻撃文字列が </script> を含むと何が起きるか説明できる

### 4. パストラバーサル対策 → safe_resolve

―――――――――――――――――――
■ 1. そもそも「パストラバーサル」って何？
―――――――――――――――――――

「パス（Path）」 = ファイルの住所（例: C:\Users\hyt15\project\data.csv）。
「トラバーサル（traversal）」 = 横断・通り抜け、の意味。

合わせて「パストラバーサル攻撃」とは、
ユーザーが入力できるパス欄に ../ (ひとつ上のフォルダへ) を混ぜて入力し、
本来見せるつもりのないフォルダのファイルを読み出す攻撃のことです。

具体例:

アプリは「project_root の中だけ」を読むつもり
攻撃者が入力欄にこう書く → ../../etc/passwd
アプリが何もチェックせずに開くと、OSのパスワードファイルなど機密ファイルが読まれる
別名: 「ディレクトリトラバーサル」「../ 攻撃」「ドットドットスラッシュ攻撃」

面接で聞かれたら一言でこう言えればOK:
「../ のような相対パスでアプリの想定外のフォルダを読まれる攻撃です。」

―――――――――――――――――――
■ 2. このアプリで攻撃が成立しうる場所
―――――――――――――――――――

app.py:949-951 を見ると、StreamlitのGUI画面で
ユーザーは「ルールファイルのパス（rules.json）」と「出力ディレクトリのパス」を
文字列で入力できるようになっています。

ここでもしユーザーが ../../Windows/System32/... のような入力をしたら、
チェックがなければアプリはそのまま読みに行ってしまいます。
だから、この2つの入力には必ず「安全化」をかけている、というのがポイントです。

―――――――――――――――――――
■ 3. 守ってる関数 safe_resolve の中身
―――――――――――――――――――

app_helper.py:79-99

def safe_resolve(raw: str, project_root: Path) -> Path | None:
try:
resolved = (Path.cwd() / raw).resolve()
except (OSError, ValueError):
return None
try:
resolved.relative_to(project_root)
except ValueError:
return None
return resolved
たった10行ですが、やってることを1行ずつ説明します。

(1) Path.cwd() / raw
　- Path.cwd() = カレントディレクトリ（今アプリが動いている場所）の絶対パス。
　- / 演算子は文字列連結ではなく「パスをつなぐ」専用の書き方。
　- 例: cwd が C:\project で raw が ../etc/passwd なら
　　C:\project\..\etc\passwd という、まだ .. が残ったままのパスができる。

(2) .resolve()
　- 「.. や . を実際に展開して、最終的な絶対パスにする」メソッド。
　- 上の例なら → C:\etc\passwd に展開される。
　- ここで初めて「本当はどこを指していたのか」が確定する。
　- ポイント: 文字列のまま .. が含まれてないか調べるのは弱い。.resolve() で展開してから判定するのが正攻法。

(3) resolved.relative_to(project_root)
　- 「展開後の絶対パスは、project_root の中にあるか？」をチェック。
　- 中にあれば成功して相対パスを返す。
　- 外にあれば ValueError を投げる。
　- 投げられたら except で None を返して呼び出し元に「危険な入力でした」と伝える。

(4) 例外を握って None 返却
　- \x00（ヌル文字）など、OSが受け付けない文字列が来ると OSError/ValueError が出る。
　- それも None で安全に弾く。

専門用語:

DictReader = CSVの1行目をヘッダ(列名)として読み、各行を辞書(キー=列名、値=セルの中身)にしてくれるPython標準の道具。
encoding="utf-8" = 文字コードの指定。日本語が文字化けしないために明示している。
―――――――――――――――――――
段階2: 入力チェック (check_rows)
―――――――――――――――――――

場所: expense_core.py:119-186

やっていること:

1行ずつ見て「形式として正しいか」を判定する。
OKだった行 → ok_rows に入れる
NGだった行 → errors に入れて、理由を文字列で添える(例: 「日付の形式が違う」「金額が数字じゃない」)
チェックしている項目は3つだけ:

必須列(date, amount, merchant, category)があるか・空欄じゃないか
日付が YYYY-MM-DD 形式か(expense_core.py:94-104 の parse_date)
金額が整数として読めるか(expense_core.py:107-116 の parse_amount)
ここの設計で面接で効くポイント:

(a) 「文字列のまま検査する」理由

もし読み込み時点で int(r["amount"]) してしまうと、不正な値("abc"とか)が来た瞬間に 例外(エラー) が飛び出す。
例外をその場で try/except で受け止めると、エラー処理コードがあちこちに散らばる。
だから「文字列のまま全行見て、ダメな行は理由つきでerrorsに避ける」方式にしている。
→ 例外処理を1ヶ所(段階2)に集中させる設計。
(b) 行番号は2から始まる(enumerate(rows, start=2))

CSVの1行目はヘッダ(列名)なので、データの最初の行は2行目。
エラー報告で「○○行目がおかしい」と人間にわかる番号を返すための工夫。
専門用語:

例外(Exception) = プログラムが続行できない異常事態。Pythonでは int("abc") のような操作で発生する。
―――――――――――――――――――
段階3: 型変換 (normalize_ok_rows)
―――――――――――――――――――

場所: expense_core.py:189-207

やっていること:

ok_rows(段階2でOKと確定した行)だけを対象に、amount を文字列から 整数(int) に変換する。
戻り値は ok_norm(normalized = 正規化された、の略)。
なぜ段階を分けるのか(面接の核心):

「段階2で 形式として正しい と確定した行だけが段階3に来るので、ここでの int() は 絶対に失敗しない 。
だから try/except で囲む必要がない。安全な前提が成立した後で型変換するから、コードがシンプルに保てる。」

これを「契約による設計(Design by Contract)」とか「事前条件をチェックしてから処理する」と言います。面接ワードとして覚えておくとカッコいい。

―――――――――――――――――――
段階4: ルール適用＋集計
―――――――――――――――――――

場所: app_helper.py:150-161 (パイプラインの呼び出し部分)

ここは段階2と並んで重要なので、コードの順序を見ます。

rows = read_csv(...) # 段階1

ok_norm = normalize_ok_rows(ok_rows) # 段階3

やっていること:

find_duplicate_candidates … 同じ日・同じ金額・同じ店の行があれば「重複の疑い」として warnings に追加。
make_summary … 月別・カテゴリ別・Top Nの合計を計算する。
ポイント:

段階4の入力は すべて段階3で型が確定した ok_norm 。だから合計を出すときに int + int で安心して足せる。
ルール違反は errors ではなく warnings に分けている(これはユニット2の項目2で詳しくやる予定)。

Q: 「このツールのデータ処理の流れを説明してください」

A: 「4段階のパイプラインです。1)CSVを文字列のまま読み込み、2)形式チェックで不正な行を errors に分離し、3)正常と確定した行だけを整数型に変換し、4)社内ルール適用と集計を行います。」

Q: 「なぜ読み込みの段階で int に変換しないんですか?」

A: 「不正な値が来たときに例外があちこちで発生し、エラー処理が散らばるからです。全行を文字列のまま検査して理由つきで errors に避け、正常確定後にまとめて型変換する設計にすることで、例外処理を1ヶ所に閉じ込められます。」

Q: 「型変換の段階で try/except がないのは大丈夫?」

A: 「直前の check_rows で parse_amount を通っており、整数化に失敗する行は事前に除外されています。事前条件が保証されているので不要です。」

### 2. errors と warnings の使い分け

質問1: 「errors と warnings の違いを30秒で説明してください」

回答の型:

「errors は 形式エラーで、後続の処理から 除外 します。warnings は ルール違反や重複候補で、データとしては正しいので clean_rows には残し、人が確認するために別ファイルに出します。」

これだけ言えれば合格ラインです。以下、なぜそう設計したかを補足します。

質問2: 「具体的に errors にはどんなものが入りますか?」

expense_core.py:119-186 の check_rows を見ると、errors に追加されるのは次の3パターンだけです:

必須列が無い・空欄 (expense_core.py:143-152)
日付の形式が YYYY-MM-DD じゃない (expense_core.py:155-157)
金額が整数として読めない (expense_core.py:160-162)
共通しているのは「そもそもデータとして壊れている」こと。日付が読めなければ月別集計はできないし、金額が文字列なら足し算できません。だから後工程に渡す前に弾きます。

コードの該当部分:

if reasons:
errors.append({...}) # 壊れている → errors 行きで除外
else:
ok_rows.append({...}) # 正常 → 後続処理へ
戻り値も (ok_rows, errors) の 2つに分けて返す (expense_core.py:186) のが分かりやすいポイントです。

質問3: 「では warnings はどんなものですか?」

warnings は2か所で生成されます。

(A) 重複候補 (rules.py:197-231)

同じ 日付+金額+店名 の行が2件以上ある場合に出ます。コメントに「重複候補は clean_rows から除外しない」と明記されています (rules.py:201)。

なぜか? → 本当に重複入力なのか、たまたま同じ昼食を2回食べたのかは 機械では判定できないからです。判断は人間に任せて、データは残します。

(B) ルール違反 (rules.py:234-467)

未登録カテゴリ・禁止ワード・上限額オーバーなど、rules.json で定義した社内ルールに反するもの。これも「データは正しいけど社内的にNG」というだけで、集計から外す理由にはならないので残します。

質問4: 「なぜ errors と warnings を分けたんですか? まとめて1つでもよくないですか?」

これが面接で必ず聞かれる本丸の質問です。回答の型はこう:

「後工程の振る舞いが違うから分けています。errors は集計に混ぜると数字が壊れるので除外必須。warnings は集計には混ぜていい(混ぜないと月次合計が実態とズレる)けど、人間に確認してほしい情報なので別ファイルで通知する、という役割分担です。」

具体的に言うと:

種類 clean_rows に残す? 集計に含まれる? 用途
errors 残さない 含まれない 「直してから再投入してね」
warnings 残す 含まれる 「これ大丈夫? 一応見ておいて」
出力ファイルも errors.csv / warnings.csv / clean.csv と分かれているので、利用者は「直すべきもの」と「確認するもの」を一目で区別できます。

質問5: 「処理の順番にも意味がありますか?」

あります。パイプラインは以下の順:

check_rows で 形式エラーを先に弾く → ok_rows と errors に分ける (expense_core.py:119)
normalize_ok_rows で 型変換(文字列 → int) (expense_core.py:189)
apply_rules でルール適用 → warnings を生成 (rules.py:234)
ポイントは 「形式エラーを弾いてから型変換する」 こと。先に int() してしまうと、文字列の金額が来たところで例外が飛んで、エラー処理がtry/exceptだらけになります。先に文字列のまま全部チェックして、安全と確定してから int 化 という流れにすることで、コードがすっきりします。

これは expense_core.py:192-193 のコメントにも「check_rows では全フィールドを文字列のまま保持している。「正常と確定した後」に型変換する」と明記されています。

ここまでで言える "面接の決めゼリフ"

「形式エラー(errors)は集計を壊すので除外、ルール違反(warnings)は人の判断が必要なので残す、と役割で分けています」
「先に文字列のまま検証して、正常確定後に型変換することで、例外処理を一箇所に集約しています」
「重複は機械で判定しきれないので、機械的に弾かず warnings として人に渡す設計です」

## 【ユニット5】

### 1. Streamlit の実行モデルと st.session_state

━━━━━━━━━━━━━━━━━━━━━━━━━━
ユニット5-1：Streamlitの実行モデルと st.session_state
━━━━━━━━━━━━━━━━━━━━━━━━━━

★ そもそも Streamlit って何？

Pythonコードだけで「ブラウザで動く画面(GUI)」を作れるライブラリ。HTMLもJavaScriptも書かない。st.button(...) とか st.file_uploader(...) みたいな関数を呼ぶと、それがそのまま画面の部品になる。

このプロジェクトでは app.py がStreamlit製のGUI、expense_tool.py がCLI(コマンドライン)で、両方とも中身の処理(パイプライン)は共通、という構成。

━━━━━━━━━━━━━━━━━━━━━━━━━━
（ここが最重要）リアクティブな再実行モデル
━━━━━━━━━━━━━━━━━━━━━━━━━━

Streamlitの一番クセのある仕様、かつ面接で必ず話題になるポイント。

普通のWebアプリ(例:Flask)の動き
　→ ボタンを押す → そのボタン専用の関数だけが呼ばれる

Streamlitの動き
　→ ボタンを押す、入力を変える、チェックを入れる…何か操作するたびに スクリプト全体が一番上から下まで丸ごと再実行される

「再実行(rerun)」と言う。ユーザー操作のたびに app.py を頭から実行しなおしている、というイメージ。

app.py:1044-1045 を見るとわかりやすい。

Streamlit はスクリプトを上から実行するので、最後に入口関数を呼ぶ。

main()
main() がファイル末尾に書いてあるのは、再実行のたびに上から下に流れていくから。

専門用語の補足
　・リアクティブ … 「入力が変わったら勝手に画面が反応して更新される」という方式
　・再実行モデル … 上記のとおり、操作ごとにスクリプトを丸ごと再実行する設計

━━━━━━━━━━━━━━━━━━━━━━━━━━
で、何が困るのか？
━━━━━━━━━━━━━━━━━━━━━━━━━━

スクリプトが毎回頭から走り直す＝普通のローカル変数は毎回ゼロから作り直される。

例：
　1. ユーザーがCSVをアップロードして「実行」を押す
　2. 重い集計処理が走って結果が出る (result というローカル変数に入る)
　3. ユーザーが画面のタブを切り替える(これも操作なのでrerun発生)
　4. スクリプトが頭から再実行される
　5. でも今回は「実行」ボタンを押してないので、result が空っぽに戻る → 画面から結果が消える！

これだと使い物にならない。「さっきの結果」をrerunを跨いで覚えておく仕組みが必要になる。それが st.session_state。

━━━━━━━━━━━━━━━━━━━━━━━━━━
st.session_state の役割
━━━━━━━━━━━━━━━━━━━━━━━━━━

ざっくり言うと「ブラウザのタブ単位で生き続ける、Python辞書(dict)っぽい入れ物」。

ローカル変数 → 関数を抜けたら消える、rerunでも消える
session_state → rerunしても消えない、ブラウザを閉じるまで生き続ける

書き方も普通のdictと同じ。

実物を見てみる。app.py:43

LAST_RUN_KEY = "last_run"
「last_run」というキー名でしまう、という宣言。文字列を直接書くとタイポ(打ち間違い)で別キーにしまう事故が起きるので、定数にしている。

app.py:1015-1018 で保存してる場所。

if result is not None: # Streamlit は操作のたびにスクリプト全体を再実行する。# session_state に保存しておくことで、rerun 後も結果表示を保てる。
st.session_state[LAST_RUN_KEY] = result
app.py:1023-1026 で読み戻してる場所。

last_run = st.session_state.get(LAST_RUN_KEY)
if last_run is None:
\_render_empty_state()
return
.get(キー) を使ってるのは、「まだ一度も実行してない初回アクセス」のときキーが存在しないから。dictの [キー] だと KeyError で落ちるが、.get() ならキーが無いときは None を返してくれる。だから直後の if last_run is None: で「まだ何も実行されてない状態」と判定して、空っぽの案内画面 (\_render_empty_state()) を出している。

━━━━━━━━━━━━━━━━━━━━━━━━━━
main() 全体での「保存 → 読み戻し」の流れ

Q1.「Streamlitの実行モデルを説明してください」
A. 「Streamlitはリアクティブな再実行モデルを採用していて、ユーザーが何か操作するたびにスクリプト全体が頭から再実行されます。なのでローカル変数は毎回リセットされます。」

Q2.「じゃあ、前回の処理結果はどう保持してるんですか？」
A. 「st.session_state という、ブラウザセッション単位で生き残る辞書ライクな入れ物に保存しています。rerumを跨いでも消えないので、これに集計結果を入れておいて、次の描画フェーズで取り出して表示しています。」

Q3.「なぜそう設計したんですか？」
A. 「実行は重い処理なのでボタンを押したときだけ動かしたい。一方タブの切り替え程度の軽い操作でも再実行は走るので、結果データだけは session_state に永続化して、描画は毎回そこから読み戻す構成にしました。これで『実行する処理』と『描画する処理』を分離できます。」

Q4.「st.session_state[キー] ではなく .get() を使ってるのはなぜ？」
A. 「初回アクセス時はまだキーが無いので、[キー] だとKeyErrorになります。.get() は無いとき None を返すので、それで初回かどうか判定して空状態の案内画面を出しています。」

### 3. UI と非UIロジックの分離

そもそも「UI と非UIロジック」って何？

UI（ユーザーインターフェース）= 画面に関する処理

ボタンを置く、文字を表示する、タブを切り替える、エラーを赤字で出す、など
このプロジェクトでは Streamlit（st.~）を使っている部分
非UIロジック = 画面と関係ない、データを動かす処理

CSVを読む、ルールでチェックする、集計する、ファイルに書き出す
Streamlit が無くても、コマンドラインからでも動く処理
「分離する」= この2つを別々のファイルに分けて書く、という設計の話。

このプロジェクトでの分離のされ方（実際のコードで確認）

ありがちな失敗パターンを2つ並べると分かります。

パターンA: テストはあるけど、CIで回してない
　→ 開発者が手元で「pytest 走らせるの忘れてた」となった瞬間、壊れたコードが main に入る。
　→ テストは "走らせて初めて" 価値がある。書いて満足は意味なし。

パターンB: CIは設定してあるけど、テストの中身がない
　→ pytest は走るが、確認している項目が無いので「常に成功」になる。
　→ 緑のチェックマークが付いているのに実は何も保証していない、という最悪の状態。

つまり、

テスト = 「何を保証するか」（中身）
CI = 「いつ・どこで保証するか」（実行タイミングの自動化）
役割が違うので、片方だけでは品質保証として成り立たない。だからセットで語る。

【面接で聞かれそうな質問】「CIって何ですか？このプロジェクトではどう使ってますか？」

まずは答えの型から。

「CIは Continuous Integration（継続的インテグレーション）の略で、コードを変更するたびに自動でチェックを走らせる仕組みです。このプロジェクトでは GitHub Actions を使って、push と Pull Request のタイミングで ruff・mypy・pytest の3つを自動実行しています」

これが言えれば60点。あとは中身を一段深く理解しておけば満点です。

【1】そもそも GitHub Actions とは（30秒で）

GitHub Actions = GitHub が用意してくれている「自動でコマンドを走らせる場所」。

リポジトリに .github/workflows/ というフォルダを作って、中に YAML ファイル（設定ファイル）を置くと、GitHub が「お、設定ファイルがあるな」と読み取って、決められたタイミングで決められたコマンドを実行してくれます。

自分のPCではなく、GitHub が用意したクリーンな仮想マシン（Ubuntu）で動くので、「自分のPCだから動いた」みたいな事故を防げます。

【2】.github/workflows/ci.yml を上から読む

ブロックごとに読み解きます。

(a) いつ動くか（ci.yml:5-7）

on:
push:
pull_request:
「push されたとき」と「Pull Request が作られた／更新されたとき」に自動実行。
→ つまり、コードを GitHub に上げる or PR を出すたびに毎回チェックが走る。

(b) どこで動くか（ci.yml:11）

runs-on: ubuntu-latest
GitHub が用意した最新の Ubuntu（Linuxの一種）の上で動く。

(c) どの Python バージョンで動かすか（ci.yml:12-15）

strategy:
matrix:
python-version: ["3.10", "3.11", "3.12", "3.13"]
ここがポイント。matrix（マトリクス）= 同じ手順を複数の組み合わせで並列に回す仕組み。
→ Python 3.10 / 3.11 / 3.12 / 3.13 の4つで同時にテスト。
→ 「このアプリは Python 3.10〜3.13 のどれでも動く」を毎回証明している。

(d) 何をするか（ci.yml:16-27）

steps は上から順番に実行されます。

順 コマンド 意味
1 actions/checkout@v4 リポジトリのコードを仮想マシンにダウンロード
2 actions/setup-python@v5 指定バージョンの Python をインストール
3 pip install --upgrade pip pip 自体を最新化
4 pip install -r requirements-dev.txt 開発用ライブラリを入れる
5 ruff check . linter（書き方チェック）
6 mypy . 型チェック
7 pytest -q テスト実行
5・6・7 がいわゆる「CIの3点セット」です。

【3】3点セットそれぞれの役割（ここが面接の本丸）

3つとも「コードの品質をチェックする」道具ですが、見ている層が違います。

(1) ruff check . → linter（リンター）

何をする？: コードの「書き方」をチェック。例えば「使ってない変数」「インポートしたけど使ってないライブラリ」「PEP8というPythonの書き方ルール違反」などを検出。
例えるなら: 文章で言う「誤字脱字・改行ミスのチェック」。
速い: ruff は Rust 製でめちゃくちゃ速い。これが採用理由としてよく挙がる。
(2) mypy . → 型チェッカー

何をする？: 関数の引数や戻り値の「型」が合っているかチェック。例えば def add(a: int, b: int) -> int と書いた関数に文字列を渡してたら警告が出る。
例えるなら: 文章で言う「主語と述語が噛み合ってるかチェック」。
なぜ必要？: Python は動かしてみるまで型エラーがわからない言語（動的型付け）。mypy を入れると、実行する前に型の不整合を見つけられる。
(3) pytest -q → テストランナー

何をする？: tests/ フォルダにあるテストコードを実際に動かして、コードの「動作」が正しいか確認。-q は quiet（出力を簡潔に）の意味。
例えるなら: 文章で言う「内容が事実と合ってるかのファクトチェック」。
【面接で聞かれそうな質問】「なぜ3つ全部やるんですか？1つでよくないですか？」

これは絶対聞かれるので答えを用意。

「3つは見ている観点が違うからです。ruff は書き方、mypy は型、pytest は実際の動作。例えばテストが通っても、型がおかしいとリファクタ時にバグります。逆に型が合っててもロジックが間違っていればテストで落ちます。3つを重ねることで、書き方・型・動作の3層で品質を担保しています」

【面接で聞かれそうな質問】「CI が落ちたらどうなるんですか？」

GitHub の PR 画面に赤い ✕ マークがつき、マージ（取り込み）の前に気付ける。
「壊れたコードが master ブランチに入るのを防げる」のが最大のメリット。
1人開発でも有効: 自分のミスを GitHub が指摘してくれるので、レビュアーがいない開発でも品質が保てる。
【4】「テストとCIをセットで語る」の意味（ユニット6の核心）

テストだけある → 走らせ忘れたら意味ない。「動くはず」が「動かない」になる。
CIだけある → 中身が空ならただの飾り。
セットで初めて「コードを変えるたびに、自動で、必ず、品質チェックされる」が成立する。
→ 面接で「テストとCIどうしてますか？」と聞かれたら、必ずセットで答えるのが正解。

【5】30秒で言える要約（暗記用）

「GitHub Actions で CI を組んでいて、push と PR のたびに Python 3.10〜3.13 の4バージョンで並列にチェックを走らせています。中身は ruff（書き方）・mypy（型）・pytest（動作）の3点セットで、書き方・型・動作の3層で品質を担保しています」
